# Thumbnail Library, explicit sync and responsive admission

## User-approved behavior

- Upload Engine keeps Choose File and adds a Thumbnail Library popup beside it. The popup has a grid, authenticated previews, Use, individual Delete, checkbox Delete Selected, Refresh and bulk Add Thumbnails.
- Bulk files are uploaded as separate asynchronous requests, serially. Each file has a progress bar and state (Waiting, Uploading %, Validating and saving, Saved/error); completed/total stays visible. Invalid files do not stop later files. The popup can be closed/reopened while uploading; the same-page job state is retained. Cancel remaining aborts the active request and skips later files. An interrupted request can have reached the server: refresh the library before retrying. A full page reload/navigation can interrupt uploads.
- Progress nodes are reused, so progress events do not rebuild the entire file list. Image grid previews load lazily. File validation/hashing runs in FastAPI worker threads.
- A matching filename is never silently overwritten. Replace matching filenames is an explicit checkbox plus confirmation; queued/failed/in-progress references block replacement. Successful replacement gives the new version a new opaque identity so stale selections are rejected. New file/DB identity is committed before old file cleanup; an interrupted replacement can leave an unindexed old blob for storage review, never an overwritten queue input.
- Dropdown selection still only selects the video. Explicit Sync Sheet fills Title/Description and matches `u1.mp4` to `u1.jpg`, `u1.jpeg` or `u1.png` in the owner's library. Exactly one match selects it and shows the existing-style preview. Missing/ambiguous matches clear stale thumbnail selection and explain manual selection. No thumbnail sheet column is needed.
- Choose File overrides the library selection; Use overrides the manual file. A new video/manual source URL clears the previous thumbnail. Selection/text/thumbnail changes during metadata requests invalidate stale responses. Other upload controls remain manual.
- Add Video to Queue now submits asynchronously, immediately disables duplicate clicks and shows an animated spinner. Browser upload progress covers details/thumbnail transfer; subsequent status explains that the server is verifying/preparing the MP4. The full MP4 copy/SHA handoff runs off the ASGI event loop. Success appears only after durable queue admission; there is no provisional 'queued' claim before source verification. No automatic request resubmission occurs after uncertain network outcomes; users are directed to inspect Queue. Existing owner-wide duplicate protection remains authoritative.

## Storage, validation and security

- Originals are private under `<uploader-data>/thumbnail-library/<sha256(owner)>/<opaque-id>.<jpg|jpeg|png>`. Browser filenames are metadata, never filesystem paths. Previews are authenticated owner-scoped GETs with no-store/nosniff headers. All mutations use authenticated owner-scoped, CSRF-protected, Concat-only POSTs behind the existing gateway.
- Pillow validates/decode-checks JPG/PNG bytes, matching extensions, maximum 50 MB per file and maximum 40 megapixels. Malformed/truncated files, symlink storage/leaves, arbitrary paths, changed size/checksum and insufficient disk reserve are rejected. Pillow is an explicit runtime dependency in pyproject.toml.
- Additive `concat_thumbnails` stores owner/name/identity/checksum metadata; `concat_thumbnail_uses` binds exact versions to projects and retains application receipts. Library selection is copied into isolated private uploader staging. The queue INSERT and reference binding share one SQLite transaction; concurrent deletion/replacement cannot bind a stale identity. No hardlinks or mutable shared upload inputs are used. The references deliberately survive original deletion to preserve history.
- Individual/bulk manual delete requires confirmation in the UI and is checked again server-side against queue references. Queued, active, paused and retryable failed uses remain protected. Separate requests are serialized by SQLite write transactions. Independently verified/applied jobs no longer need the original and cannot deadlock each other during cleanup.
- Library items are separate from Google Drive and Concat rendering storage. No Drive object, GPU code, OAuth inventory or channel sheet is changed. Library APIs neither import channels nor start uploads.

## Verified cleanup and failure recovery

1. The video must have the existing independent YouTube API verification receipt and YouTube ID.
2. A library thumbnail additionally requires successful application: the corresponding core `thumbnail_stage_state=SUCCEEDED` checkpoint, or a successful thumbnail-only `thumbnails.set` recovery call against that exact verified video. `applied_at` is persisted before any cleanup.
3. If thumbnail application failed or was not confirmed, keep originals/private inputs and the verified-video receipt. The persisted cleanup loop retries only thumbnail application/cleanup; it never submits another video upload.
4. After confirmation, remove the exact library original and private thumbnail copy. The library ID, fingerprint and successful receipts are checked again. If another unverified queue entry still uses the original, retain it with cleanup pending and eventually retry after the dependency finishes/cancels.
5. Deletion errors retain the pending marker and use the existing persisted 60-second minimum retry backoff. A restart or archived queue entry does not discard the obligation. Missing file/row after partial cleanup is idempotently reconciled. YouTube IDs/URLs, queue history, thumbnail-use/application receipts and logs remain.
6. The library original/private-thumbnail cleanup is independent of the optional generic staged-video cleanup setting. Existing manual-file-only and other uploader behavior is retained.

Existing metadata, media-picker, channel-picker, thumbnail-limit and Salad UI Node suites pass, as do Python compile, new JavaScript syntax and diff checks.

New tests cover real images, damaged/oversize/mismatched formats, owner/CSRF isolation, authenticated previews, symlinks, duplicate/replace behavior, shared busy references, partial bulk delete, concurrent same-name adds, stale admission rollback, schema restart, JSON queue admission/duplicate rejection, verified cleanup, failed thumbnail-only recovery, cleanup retry without reupload, and eventual shared-source cleanup.

CI extends the real Chromium test at 1440, 1024, 760, 390 and 320px. It uses real templates/styles/scripts with locally fulfilled network responses and deliberately held uploads/admission responses: per-file bars, failure continuation, closing/reopening during upload, responsive controls, preview/manual override, selected deletion, immediate queue spinner, duplicate-submit blocking, error recovery and success navigation. The local executor cannot launch Chromium due to denied sockets; CI results are authoritative before the user-authorized merge.

All tests use temporary storage and mocked remote APIs. No live Google/YouTube upload, production media deletion, deployment, Drive or GPU operation is performed. A real thumbnail API/OAuth smoke remains a user-controlled release validation. Deploy only after merge using the existing exact-main-SHA guarded procedure. Back up uploader SQLite and the thumbnail-library directory. Rollback code may leave the additive tables in place; preserve all queue/remote/application receipts and do not recreate verified upload jobs to repair cleanup.
